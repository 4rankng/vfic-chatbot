# Agent Development Kit

The repository separates agent behavior into three layers. This keeps
startup context small and makes safety rules more reliable.

## Layers

1. **Rules:** `.claude/rules/` holds the durable repository rules (workflow,
   development, orchestration, review) that the harness loads into context;
   root `AGENTS.md` is the always-loaded repository constitution, and
   `scripts/check-doc-links.mjs` gates its routing.
2. **Skills:** `.claude/skills/` contains task-specific workflows that load on
   demand and route to existing source-of-truth documents.
3. **Hooks:** `.claude/settings.json` is the single registration point for the
   shared hooks implemented by the `.claude/hooks/*.cjs` scripts. Do not add a
   second manifest such as `.claude/hooks/hooks.json`: Claude Code does not read
   one, and a duplicate registration runs every hook twice per event. (`ak kit
   init` may reinstall that plugin-form file; delete it again if it appears.)

Personal permissions and experimental settings belong in
`.claude/settings.local.json`.

## Configuration authority

Three directories touch agent configuration, and none of them overlaps another:

- `.claude/` is machine-local and untracked (see `.gitignore`):
  `settings.json` (hook registration), `hooks/`, `skills/`, `agents/`,
  `rules/`, `output-styles/` are installed per machine, so every durable rule
  lives in the tracked sources.
- `.agentkit/config.yaml` is the versioned AgentKit settings file for this
  repository — per-hook toggles, coding level, path layout. Every other file in
  `.agentkit/` is installer output regenerated by `ak kit init` and stays
  ignored.
- `.omc/` holds runtime state only and is never committed.

They therefore answer different questions: `.claude/settings.json` decides which
hooks exist and when they fire, `.agentkit/config.yaml` decides whether a given
hook is enabled in this repository, and `.omc/` records what the runtime did.

## Guard behavior

Each hook reads Claude Code's JSON event from standard input and returns either
nothing — leaving normal permission handling intact — or a decision:

- `privacy-block.cjs` blocks reads and writes of sensitive files (`.env`,
  credentials, keys). After the user approves one specific path, retry with the
  literal `APPROVED:` prefix; approval is per path, never blanket.
- `scout-block.cjs` blocks access to directories matched by `.claude/.ckignore`
  (vendored code, build output) while still allowing build commands that merely
  traverse them. A project-local `.claude/.ckignore` overrides the baseline.
- `descriptive-name.cjs` adds file-naming guidance to `Write` calls and never
  blocks.
- `secret-output-guardrail.cjs` and `simplify-gate.cjs` run on every prompt. The
  first injects a do-not-echo-credentials reminder when the prompt indicates
  secret handling and never echoes prompt text; the second warns on
  `commit`/`finalize`/`release` and blocks `ship`/`merge`/`pr`/`deploy`/`publish`
  while the working tree carries a large unsimplified diff
  (`CK_SIMPLIFY_DISABLED=1` bypasses it).

The blocking guards fail open: an unexpected error exits without a decision.
They are workflow guardrails, not a security sandbox. Shell commands can be
constructed in many ways, and semantic changes such as an incompatible API
contract cannot be classified reliably from a path alone. The durable rules in
`.claude/rules/` still apply even when the hook stays silent.

## Verification

In Claude Code, `/hooks` shows the registered shared project hooks. Registration
lives in exactly one file, `.claude/settings.json`, so each hook fires once per
event.

`scripts/agent/test-project-guard.py` targets `.claude/hooks/project-guard.py`,
which this repository does not register, so it does not exercise the live
guards.

The hook configuration follows the official project settings and `PreToolUse`
decision contract documented at <https://code.claude.com/docs/en/hooks>.
