# Agent Completion Checklist

## Task record

- Task: Per-project external API integration + the `call_project_api` agent tool, so the bot can resend a password-reset OTP (or run any admin-documented operation) against an employer's own system and answer truthfully from the real response.

## Result

- Overall status: PASS
- Remaining risks or follow-ups:
  - **No per-endpoint write gate (accepted).** The operator chose guide-driven authority: any `POST` the guide describes is callable while the integration is enabled. Compensating controls are the fixed origin, the `GET`/`POST` limit, the param bounds, and the 60 s mutate window. Recorded in ADR-0011.
  - **Live-vendor paths unverified.** The success/rate-limit/off-origin/not-configured paths are proven against a real loopback HTTP server, real Postgres and real Redis, but no credentials exist in this environment to exercise the employer's real `401`/`429`/`reset` behaviour.
  - **Capability assumption — RESOLVED in production (2026-09-26).** The tool was granted through the `knowledge` capability on the assumption that the active revision selected it. Production has no active manifest at all (`installation_state` 0 rows, `installation_manifest_revisions` 0 rows), so the legacy `_agent_turn` path runs: that is the path carrying the prompt block, and `TOOL_SCHEMAS` is bound unfiltered, so `call_project_api` is reachable. The `job_advisory` contingency cannot fire. See the deploy report for the query.
  - **Operator-visible dev state:** the LG Display Bắc Ninh project now stores the operator's real `guide.md` with a placeholder key and `enabled=false`, so the bot's behaviour for that project is unchanged until an admin enables it.
  - The `tt-dev` background app stack (uvicorn + RQ workers + vite + zalo mock) started for the UI proof was stopped after capture; the `make db` containers (postgres, redis, adminer at `http://localhost:8082`) are left running, as the plan's verification step 1 expects, so the stored row can be inspected.
