## 1. Overview

### 1.1 Company mission

> Bên cty mình có những ý chính sau đây cần làm, sau này có thể mở rộng hơn. Cty
> muốn có một chatbot nói chuyện với người lao động để tư vấn người lao động tìm
> được việc làm phù hợp với hoàn cảnh từng người. Cty muốn chatbot:

- Tư vấn người lao động dựa vào kiến thức, tài liệu của cty, không trả lời ngoài lề.
- Xác định người lao động nào có mong muốn làm việc, bỏ qua những người hỏi chơi không hứng thú.
- Chuyển danh sách những người có nhu cầu về trang web của công ty để nhân viên tuyển dụng follow up, hoặc để chatbot tự follow up thuyết phục người lao động đăng ký ứng tuyển.
- Nhân viên tuyển dụng có thể can thiệp bất kỳ đoạn chat nào; nếu có người can thiệp thì chatbot không tiếp tục nữa.

**In short:** a Zalo chatbot that consults workers using VFIC's knowledge base, qualifies the interested ones into leads, and lets recruitment staff take over any conversation — at which point the bot must stop.

### 1.2 Current state

- **n8n** is hosted on DigitalOcean (VPS 1 vCPU, 2 GB RAM, 50 GB SSD). It hosts the ChatBot workflow: whenever a user interacts with the Zalo Bot, the message is sent to the n8n ChatBot workflow.
- The ChatBot's mission today is to consult users given the knowledge provided by VFIC.
- The ChatBot saves **leads** to the `leads` table in Supabase.
- The ChatBot's memory and conversation history are saved in Supabase.

The bot is a stateless pipeline:

```
Zalo Message -> Dedup Message -> Normalize Message -> Typing... ->
AI Agent -> [Chat Reply, Build Persistence Payload -> Persist Lead + Persist Memories]
```

Existing Supabase tables (project `vichwmxeptglqmzefsiq`):

| Table | Purpose |
|---|---|
| `leads` | Worker profiles, keyed by `zalo_id`; `lead_score` ∈ hot/warm/not_interested |
| `documents` | Knowledge-base vector table; `drive_file_id` is a generated column |
| `memories` | Per-candidate semantic memory (vector) |
| `vfic_chat_histories` | LangChain memory blob (`session_id` + `message` jsonb) — **not** a displayable transcript |
| `vfic_message_dedup` | MD5-of-text dedup with an 8-second window, for Zalo double-delivery only |

### 1.3 The problem

Users currently have **no interface** to monitor conversations, take over a chat from the ChatBot, view statistics/metrics, or access lead information.

### 1.4 Product goal

Build a **miniCRM + live chat console** for VFIC recruiters to:

1. Monitor all Zalo chatbot conversations
2. Take over any chat from the chatbot
3. Stop the chatbot when a recruiter takes over
4. View and manage worker leads
5. Assign leads to recruiters
6. Follow up with interested workers
7. Manage jobs and company knowledge used by the chatbot
8. Track basic recruitment and chatbot metrics

## 2. System architecture

### 2.1 Separation of concerns (the four pillars)

The miniCRM must **not** replace n8n. The correct separation is:

| Component | Role |
|---|---|
| **miniCRM** | Human operation console |
| **n8n** | Chatbot workflow automation |
| **Supabase / Postgres** | Source of truth |
| **Zalo OA** | Communication channel |

### 2.2 Does the admin web need its own database?

**No.** One Supabase Postgres is the single source of truth. The admin web is a **thin React client**: Supabase JS for auth, RLS-gated reads/writes, and Realtime subscriptions; Supabase Storage for uploaded KB docs. It owns only static build assets (hosted on Vercel / Netlify / etc.) and ephemeral UI state — no data database of its own.

Two access patterns into the **same** database:

- **Bot (n8n):** Postgres node, direct DB connection, **bypasses RLS** (trusted infrastructure).
- **Admin web:** Supabase JS with the user's JWT, **subject to RLS**.

> If analytics/BI isolation is ever needed later, use a read-replica or a separate schema — not a separate app DB.

### 2.3 Tech stack

**Frontend:** React + TypeScript + Vite, Bootstrap 5, Tabler UI template, Tabler Icons, React Router, TanStack Query or SWR, Supabase JS client (auth + realtime).

Tabler is a responsive Bootstrap 5 admin template with built-in dashboard layouts, dark mode, forms, tables, charts, maps, and UI components; Tabler Icons are MIT-licensed and usable commercially. Supabase RLS enforces admin/recruiter access rules at the database level since the frontend talks directly to Supabase.

**Backend (Option A — fastest MVP):** Supabase Auth, Supabase Postgres, Supabase Realtime, Supabase Storage, Supabase RPC / Edge Functions, n8n webhook workflows.

> Supabase Realtime can listen to Postgres changes, which powers live conversation updates in the miniCRM.

### 2.4 Component interaction

## 4. Data model

### 4.1 Existing tables (reuse)

Reuse as-is: `documents` (KB), `memories` (per-candidate memory), `vfic_message_dedup` (delivery dedup). Extend `leads` (add `assigned_recruiter_id`, a `status` enum for stages, and an FK to conversations — see [§7.5](#75-leads)).

> **contact = lead:** there is no separate contacts table. The worker identity is the `leads` row keyed by `zalo_id`, which the bot already upserts via *VFIC Persist Lead*.

### 4.2 New tables (DDL — create as a Supabase migration)

```sql
-- enums
CREATE TYPE conversation_mode   AS ENUM ('BOT','HUMAN');
CREATE TYPE conversation_status AS ENUM ('OPEN','CLOSED');
CREATE TYPE message_sender      AS ENUM ('WORKER','BOT','RECRUITER','SYSTEM');

-- profiles: minimal RBAC (auth.uid() FK + future frontend); auto-create on signup
CREATE TABLE profiles (
  id        uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  role      text NOT NULL DEFAULT 'recruiter' CHECK (role IN ('admin','recruiter')),
  full_name text,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
BEGIN INSERT INTO public.profiles (id) VALUES (NEW.id); RETURN NEW; END; $$;
CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

-- conversations (join key = the existing Zalo chat_id, so the bot needs no new id)
CREATE TABLE conversations (
  id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  zalo_chat_id          text UNIQUE NOT NULL,
  mode                  conversation_mode   NOT NULL DEFAULT 'BOT',
  status                conversation_status NOT NULL DEFAULT 'OPEN',
  needs_human           boolean NOT NULL DEFAULT false,   -- "Cần người xử lý" escalation flag
  version               int  NOT NULL DEFAULT 1,          -- optimistic lock; bumped on every ownership transition
  assigned_recruiter_id uuid REFERENCES profiles(id),
  taken_over_at         timestamptz,
  last_message_at       timestamptz,
  created_at            timestamptz NOT NULL DEFAULT now(),
  updated_at            timestamptz NOT NULL DEFAULT now()
);

-- messages (structured transcript; written by bot AND human)
CREATE TABLE messages (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id uuid NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  sender          message_sender NOT NULL,
  recruiter_id    uuid REFERENCES profiles(id),            -- set when sender = RECRUITER
  body            text NOT NULL,
  zalo_message_id text,                                     -- inbound idempotency
  delivery_status text NOT NULL DEFAULT 'sent'
                  CHECK (delivery_status IN ('sent','suppressed','failed','pending')),
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX messages_conv_idx ON messages (conversation_id, created_at);
CREATE UNIQUE INDEX messages_zalo_uidx
  ON messages (conversation_id, zalo_message_id) WHERE zalo_message_id IS NOT NULL;

-- updated_at
CREATE OR REPLACE FUNCTION public.touch_updated_at() RETURNS trigger
  LANGUAGE plpgsql AS $$ BEGIN NEW.updated_at=now(); RETURN NEW; END; $$;
CREATE TRIGGER conversations_touch BEFORE UPDATE ON conversations
  FOR EACH ROW EXECUTE FUNCTION public.touch_updated_at();
```

### 4.3 Field decisions

- `mode` {BOT, HUMAN} — **who is handling** the chat.
- `status` {OPEN, CLOSED} — **lifecycle**.
- `needs_human` (boolean) — the **"Cần người xử lý"** escalation flag. Chosen over a third `PENDING_HUMAN` mode value to keep "who handles" separate from "needs attention".
- `version` — optimistic lock; bumped on every ownership transition (take over / release).
- The suppressed `messages` row stores the bot's **proposed reply** so a recruiter can see what the bot was about to send.

## 5. Human takeover (core feature)

### 5.1 Requirement & the "cancel" problem

**Important rule:** when a recruiter takes over, the chatbot must stop immediately, and any in-flight bot reply must not reach the worker.

n8n executions **cannot be cancelled externally**. So "cancel the pending bot reply" describes the *outcome*, not the mechanism. The correct model is **check-before-send**: the bot checks whether it still owns the conversation and, if not, silently drops the reply.

### 5.2 Mechanism — two guard points

1. **Run-start guard** — when a new inbound arrives, if `mode = HUMAN` the bot logs the worker's line (so the recruiter still sees it) and **stops**: no typing, no AI. This is "the bot is off for this chat."
2. **Pre-send guard** — immediately before the Zalo send, re-check `mode = 'BOT' AND version = version_at_start`. If it fails, write a `messages` row with `delivery_status = 'suppressed'` (storing the bot's proposed reply) and **stop**.

The recruiter's `take_over_conversation()` is an **atomic, transactional flip** (`mode → HUMAN`, `version++`) that the bot's guard then observes on its next read. Checking **both** `mode` and `version` also kills **stale** runs (e.g. recruiter took over *then* released back to BOT during one bot run: `mode` is BOT again but `version` changed, so the original run's reply is correctly suppressed).

> The only unavoidable residual race window is the sub-second gap between the pre-send check and the Zalo HTTP call — Zalo is an external, non-transactional API. For a recruitment chat this is acceptable; tighter options exist (§5.3).

### 5.3 Send-design alternatives (CHOSEN: Design 1)

| | Design 1 — guard node | Design 2 — Edge Function | Design 3 — transactional outbox |
|---|---|---|---|
| Idea | Keep the bot's direct `zaloBot` send; insert a Postgres ownership check right before it | Replace the direct send with a Supabase Edge Function doing check + send back-to-back; same function serves recruiter outbound | Bot writes a pending message row; a worker claims it atomically (`UPDATE … WHERE mode='BOT'`) and sends |
| Race window | n8n inter-node latency (largest, variable) | ~tens of ms (function latency) | Effectively closed at the check |
| New infra | None | Deno function + Zalo token in Supabase secrets | Worker + monitoring |
| MVP fit | ★★★★★ | ★★★ | ★★ |

The data model in [§4](#4-data-model) is **identical for all three**, so starting with **Design 1** does not preclude graduating to Design 2 or 3 later if leakage is observed in production.

### 5.4 Takeover / release RPCs

Atomic, `SECURITY DEFINER` (bypass RLS safely; authorization is checked *inside*). `take_over_conversation` flips mode + assigns + bumps version + resets `needs_human` + inserts the SYSTEM message — **all in one transaction**, so a concurrent bot guard read after commit sees `HUMAN`, and two recruiters racing cannot split ownership (exactly one wins, the other raises).

```sql
CREATE OR REPLACE FUNCTION public.take_over_conversation(p_zalo_chat_id text, p_recruiter_id uuid)
RETURNS uuid LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
DECLARE v_conv uuid; v_owner uuid;
BEGIN
  SELECT assigned_recruiter_id INTO v_owner FROM conversations WHERE zalo_chat_id=p_zalo_chat_id;
  IF v_owner IS NOT NULL AND v_owner <> p_recruiter_id THEN
    RAISE EXCEPTION 'conversation already owned by another recruiter';
  END IF;
  INSERT INTO conversations (zalo_chat_id, mode, assigned_recruiter_id, taken_over_at, version)
  VALUES (p_zalo_chat_id,'HUMAN',p_recruiter_id,now(),2)
  ON CONFLICT (zalo_chat_id) DO UPDATE
    SET mode='HUMAN', assigned_recruiter_id=p_recruiter_id, taken_over_at=now(),
        needs_human=false, version=conversations.version+1
  RETURNING id INTO v_conv;
  INSERT INTO messages (conversation_id, sender, body)
  VALUES (v_conv,'SYSTEM','Cuộc hội thoại đã được chuyển cho nhân viên.');
  RETURN v_conv;
END; $$;

CREATE OR REPLACE FUNCTION public.release_to_bot(p_zalo_chat_id text, p_recruiter_id uuid)
RETURNS uuid LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
DECLARE v_conv uuid;
BEGIN
  UPDATE conversations SET mode='BOT', version=version+1
  WHERE zalo_chat_id=p_zalo_chat_id AND assigned_recruiter_id=p_recruiter_id
  RETURNING id INTO v_conv;
  IF v_conv IS NULL THEN RAISE EXCEPTION 'not owner or not found'; END IF;
  INSERT INTO messages (conversation_id, sender, body)
  VALUES (v_conv,'SYSTEM','Cuộc hội thoại đã được trả lại cho chatbot.');
  RETURN v_conv;
END; $$;
```

### 5.5 n8n bot modifications

Edit **`VFIC-Chatbot.json`** (workflow id `iodmXzjRe03KqPdB`) **in place** — do not create a new workflow. Keep `active: false` until acceptance tests pass. New chain (added nodes in [brackets]; `Normalize` also exports `msg_id` from the Zalo payload — confirm exact path during edit):

```
Zalo Message -> Dedup Message -> Normalize Message
  -> [Ensure Conversation]      (Postgres)  upsert, RETURN id, version, mode (v0=version)
  -> [Insert Inbound Message]   (Postgres)  WORKER msg, idempotent on zalo_message_id
  -> [Run-Start Guard]          (IF)        mode='HUMAN'?
        true  -> Stop                                   (inbound already logged; no typing/AI)
        false -> Typing... -> AI Agent
                  -> [Recheck Ownership] (Postgres)  SELECT (mode='BOT' AND version=$v0) AS ok
                  -> [Pre-Send Guard]    (IF)        {{ $recheck.ok }}
                        false -> [Insert Suppressed Message] (Postgres, BOT, 'suppressed') -> Stop
                        true  -> Chat Reply (existing zaloBot)
                                 + [Insert Bot Message] (Postgres, BOT, 'sent')
                                 + (Build Persistence Payload -> Persist Lead + Persist Memories) [unchanged]
```

Node SQL:

```sql
-- Ensure Conversation   ($1 = chat_id)
INSERT INTO conversations (zalo_chat_id) VALUES ($1)
ON CONFLICT (zalo_chat_id) DO UPDATE SET updated_at=now()
RETURNING id, version, mode;

-- Insert Inbound Message  ($1=conv_id, $2=user_text, $3=msg_id)  [prefer Postgres `insert` op or a log_message() RPC for free-text]
INSERT INTO messages (conversation_id, sender, body, zalo_message_id)
VALUES ($1,'WORKER',$2,$3)
ON CONFLICT (conversation_id, zalo_message_id) WHERE zalo_message_id IS NOT NULL DO NOTHING;

-- Recheck Ownership  ($1=conv_id, $2=v0)
SELECT (mode='BOT' AND version=$2) AS ok FROM conversations WHERE id=$1;

-- Insert Suppressed / Insert Bot Message  ($1=conv_id, $2=AI reply text)
INSERT INTO messages (conversation_id, sender, body, delivery_status)
VALUES ($1,'BOT',$2,'suppressed');   -- or 'sent' for the success branch
```

**n8n implementation notes** (from n8n MCP node types):

- Postgres `executeQuery` binds params via `options.queryReplacement` — a **comma-separated** list → `$1, $2, …`. Safe for the Recheck (`conv_id`, `version`). For **free-text** inserts (the message body), prefer the Postgres node's `insert` operation (column mapping) or a typed `log_message()` RPC, to avoid the comma-split pitfall.
- IF node (v2.3): `conditions = { combinator: 'and', conditions: [...], options }`.
- Reuse the existing **Postgres account** credential and the existing **`zaloBot`** node/credential (unchanged).

### 5.6 Recruiter outbound (Phase B)

Recruiter sends → admin web inserts a `messages` row (`sender = RECRUITER`) [RLS enforces owned + HUMAN] → a pending-outbound row → an n8n webhook workflow **claims** it and sends via the existing `zaloBot` node (Zalo OA token stays in n8n, never in the browser) → updates `delivery_status`. This is a **mini-outbox** for human messages and keeps a single Zalo-send primitive.

On **Release to bot**, append the recruiter's lines into `vfic_chat_histories` so the bot's LangChain memory (session = `chat_id`) includes the human exchange and resumes with full context.

## 6. Security & realtime

### 6.1 RLS policies + grants

RLS is **frontend-facing**; the bot bypasses it via its direct DB connection. **Enabling RLS alone is not enough** — the `authenticated` role also needs table privileges or policies silently match nothing. `anon` gets nothing (the CRM is auth-only).

```sql
ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages     ENABLE ROW LEVEL SECURITY;
ALTER TABLE profiles     ENABLE ROW LEVEL SECURITY;

GRANT SELECT, INSERT, UPDATE, DELETE ON conversations, messages, profiles TO authenticated;

-- admin = all; recruiter = assigned-to-me OR unassigned; recruiter may INSERT only
-- RECRUITER messages on a conversation they own that is HUMAN.
CREATE POLICY conv_admin_all        ON conversations FOR ALL TO authenticated
  USING (EXISTS (SELECT 1 FROM profiles WHERE id=auth.uid() AND role='admin'))
  WITH CHECK (EXISTS (SELECT 1 FROM profiles WHERE id=auth.uid() AND role='admin'));
CREATE POLICY conv_recruiter_read   ON conversations FOR SELECT TO authenticated
  USING (assigned_recruiter_id=auth.uid() OR assigned_recruiter_id IS NULL);
CREATE POLICY msg_admin_all         ON messages FOR ALL TO authenticated
  USING (EXISTS (SELECT 1 FROM profiles WHERE id=auth.uid() AND role='admin'))
  WITH CHECK (EXISTS (SELECT 1 FROM profiles WHERE id=auth.uid() AND role='admin'));
CREATE POLICY msg_recruiter_read    ON messages FOR SELECT TO authenticated
  USING (EXISTS (SELECT 1 FROM conversations c WHERE c.id=conversation_id
        AND (c.assigned_recruiter_id=auth.uid() OR c.assigned_recruiter_id IS NULL)));
CREATE POLICY msg_recruiter_insert  ON messages FOR INSERT TO authenticated
  WITH CHECK (sender='RECRUITER' AND recruiter_id=auth.uid()
        AND EXISTS (SELECT 1 FROM conversations c WHERE c.id=conversation_id
                    AND c.assigned_recruiter_id=auth.uid() AND c.mode='HUMAN'));
CREATE POLICY profile_self          ON profiles FOR SELECT TO authenticated
  USING (id=auth.uid() OR EXISTS (SELECT 1 FROM profiles p WHERE p.id=auth.uid() AND p.role='admin'));
```

### 6.2 Realtime

Enroll the tables and set full replica identity so the inbox/transcript push live. **Realtime respects RLS**: a recruiter's `postgres_changes` subscription only fires for rows her `SELECT` policy allows → per-recruiter live scoping is automatic (no client-side filtering needed).

```sql
ALTER TABLE conversations REPLICA IDENTITY FULL;
ALTER TABLE messages     REPLICA IDENTITY FULL;
ALTER PUBLICATION supabase_realtime ADD TABLE conversations, messages;
```

## 7. Feature & page specs

### 7.1 Login

Route `/login`. After login: `admin → /dashboard`, `recruiter → /my-dashboard`.

### 7.2 Dashboards

**Admin dashboard** (`/dashboard`) — company-wide metrics: total conversations; new conversations today; active bot conversations; human-takeover conversations; qualified leads; applications; hires; overdue follow-ups; failed Zalo sends; n8n workflow errors.

**Recruiter dashboard** (`/my-dashboard`) — personal work only: my assigned/unread conversations; my assigned/qualified leads; my overdue/completed follow-ups; my applications; my hires.

### 7.3 Conversation inbox

Route `/conversations`.

**Admin view:** all conversations, bot conversations, pending-human conversations, human-owned conversations, closed conversations, all recruiters' conversations.

**Recruiter view:** conversations assigned to me, unassigned conversations, conversations I took over, conversations needing human support. A recruiter should not see conversations assigned to another recruiter unless an admin allows it later.

**Filters:** Tất cả · Của tôi · Chưa phân công · Cần người xử lý · Bot đang xử lý · Tôi đang xử lý · Đã đóng. For admin, add: **Theo nhân viên tuyển dụng**.

### 7.4 Conversation detail

Route `/conversations/:id`. Main actions:

| Action | Admin | Recruiter |
|---|---|---|
| Take over | Yes | Yes, if unassigned or assigned to self |
| Send message | Yes | Yes, if assigned to self |
| Assign recruiter | Yes | No |
| Release to bot | Yes | Yes, if assigned to self |
| Close | Yes | Yes, if assigned to self |
| Reopen | Yes | Yes, if assigned to self |
| Add note | Yes | Yes, if assigned to self |
| Delete message | No by default | No |

`take_over_conversation(conversation_id, recruiter_id)` must: set `mode = HUMAN`, set `assigned_recruiter_id`, increment `version`, suppress the in-flight bot reply via the pre-send guard (no kill signal — see [§5](#5-human-takeover-core-feature)), insert a system message + audit event, and push a realtime update.

### 7.5 Leads

Admin route `/leads` (all leads). Recruiter route `/my-leads` (assigned leads, leads from conversations they own, and unassigned qualified leads only if recruiter self-pickup is allowed).

**Lead stages** (keep simple):

`NEW · ENGAGED · QUALIFIED · APPLIED · HIRED · LOST · UNQUALIFIED`

`HANDED_OFF` is removed (recruiters are inside the system); handoff is represented by `assigned_recruiter_id IS NOT NULL`. Implement stages as a CHECK/enum on `leads.status`.

### 7.6 Jobs

**Admin:** create / edit / activate / pause / mark full / archive jobs.
**Recruiter:** view active jobs, search, copy job info, recommend a job to a worker, view matched leads for own leads only. Recruiters should not edit job records in the MVP.

### 7.7 Knowledge base

Only **admin** should manage company knowledge (this avoids recruiters changing what the chatbot is allowed to say). Admin can: upload document, preview extracted text, approve, archive, re-run embedding, test retrieval. Recruiters get no access (MVP recommendation) or read-only access to approved knowledge.

### 7.8 Follow-up

**Admin** sees all follow-ups and can reassign or delete any.
**Recruiter** sees only their own pending / overdue / completed follow-ups, and can: create a follow-up for an own lead, mark done, snooze, or cancel their own follow-up.

## 8. Acceptance tests

1. **Run-start guard** — set `mode = HUMAN`, send a Zalo message → one WORKER message logged, no AI run, no BOT message, no Zalo send.
2. **Pre-send guard (takeover wins)** — given `mode = BOT` and a bot reply generating, when the recruiter clicks Take over: `mode` becomes HUMAN, `version` increments, the in-flight bot reply is **suppressed** (the pre-send guard sees `mode = HUMAN` and skips the send — there is no kill signal), a BOT message with `delivery_status = 'suppressed'` (containing the proposed reply) and a SYSTEM message are written, and **no** bot message is sent to Zalo.
3. **Stale-run** — `take_over` then `release_to_bot` inside one run → the original reply is suppressed (version mismatch); a new message after release gets a fresh `sent` BOT reply.
4. **Idempotency** — replay the same inbound `zalo_message_id` → a single WORKER row.
5. **Double-takeover** — two concurrent `take_over_conversation` calls (different recruiters) → exactly one succeeds, the other raises "owned by another recruiter".
6. **Recruiter reply** — given `mode = HUMAN` and the recruiter is assigned, when the recruiter sends a message → an outbound message is created, the Zalo message is sent, and the transcript updates in realtime.
7. **Bot guardrail** — given an off-topic question, when the chatbot processes it → the bot gives a short redirect response and does not invent an unrelated answer.
8. **Lead qualification** — given a worker states job preference, location, and availability, when the qualification workflow runs → `lead_stage` becomes QUALIFIED, qualification reasons are saved, and a recruiter follow-up task is created.
9. **Design-1 window (documented, not pass/fail)** — measure the guard → send gap; confirm it is sub-second. A tighter Design 2/3 is available if leakage appears.

Flip `VFIC-Chatbot` to `active: true` only after tests 1–5 pass.

## 10. MVP definition

The first production MVP is complete when recruiters can:

- Log in
- See all Zalo conversations
- Open a conversation
- Take over from the chatbot
- Send a message to a worker
- View a lead profile
- Update a lead stage
- Assign a recruiter
- Create a follow-up task
- Close a conversation

That is the core miniCRM. Job management, knowledge approval, and analytics are important, but the first must-have is **conversation control + lead ownership**.
