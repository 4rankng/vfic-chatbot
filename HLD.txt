## 1. Overview

### 1.1 Company mission

> Bên cty mình có những ý chính sau đây cần làm, sau này có thể mở rộng hơn. Cty
> muốn có một chatbot nói chuyện với người lao động để tư vấn người lao động tìm
> được việc làm phù hợp với hoàn cảnh từng người. Cty muốn chatbot:

- Tư vấn người lao động dựa vào kiến thức, tài liệu của cty, không trả lời ngoài lề.
- Xác định người lao động nào có mong muốn làm việc, bỏ qua những người hỏi chơi không hứng thú.
- Chuyển danh sách những người có nhu cầu về trang web của công ty để nhân viên tuyển dụng follow up, hoặc để chatbot tự follow up thuyết phục người lao động đăng ký ứng tuyển.
- Nhân viên tuyển dụng có thể can thiệp bất kỳ đoạn chat nào; nếu có người can thiệp thì chatbot không tiếp tục nữa.

**In short:** a Zalo chatbot that consults workers using VFIC's knowledge base, qualifies the interested ones into leads, and lets recruitment staff take over any conversation — at which point the bot must stop.

### 1.2 Current state

- **n8n** is hosted on DigitalOcean (VPS 1 vCPU, 2 GB RAM, 50 GB SSD). It hosts the ChatBot workflow: when a user interacts with the Zalo Bot, the message goes to the n8n ChatBot workflow.
- The ChatBot consults users using VFIC's knowledge and saves **leads**, memory, and conversation history to Supabase.
- The bot is a stateless pipeline: `Zalo Message → Dedup → Normalize → Typing → AI Agent → [Chat Reply, Persist Lead + Persist Memories]`.

Existing Supabase tables (project `vichwmxeptglqmzefsiq`, schema `public`):

| Table | Purpose |
|---|---|
| `leads` | Worker profiles, keyed by `zalo_id`; `lead_score` ∈ hot/warm/not_interested |
| `documents` | Knowledge-base vector table; `drive_file_id` is a generated column |
| `memories` | Per-candidate semantic memory (vector) |
| `vfic_chat_histories` | LangChain memory blob (`session_id` + `message` jsonb) |
| `vfic_message_dedup` | MD5-of-text dedup, 8-second window, for Zalo double-delivery |

### 1.3 The problem

Users currently have **no interface** to monitor conversations, take over a chat from the ChatBot, view statistics/metrics, or access lead information.

### 1.4 Product goal & approach

Build a **miniCRM + live chat console** for VFIC recruiters. The **fastest-MVP path** is to **use [Chatwoot](https://www.chatwoot.com/)** as the recruiter's live-chat console and keep only a **small custom page** for VFIC business data, rather than building a full inbox/transcript UI ourselves.

Chatwoot already provides: conversation inbox, live chat transcript, recruiter (agent) assignment, conversation labels, internal notes, conversation status, and basic team collaboration. Its **API channel** is designed for custom platforms (like our Zalo bridge) and integrates via REST + webhooks; automation rules can route conversations, assign agents, add labels, and trigger actions.

So the split is:

- **Chatwoot** = live chat layer (inbox, transcript, agents, labels, notes, status, collaboration).
- **VFIC data in Supabase** = `leads` (+ `lead_stage`, `intent_score`), `jobs`, `knowledge_documents`, `follow_up_tasks`, `bot_runs`, `conversations` (`mode`/`version`). Kept outside Chatwoot so it stays queryable and owned by VFIC.
- **n8n** = the bridge: Zalo ↔ Chatwoot ↔ Supabase.

Recruiters must be able to: monitor all Zalo chatbot conversations; take over any chat (which stops the bot); view/manage worker leads; assign leads; follow up with interested workers; manage jobs and knowledge; and track basic metrics.

## 2. System architecture

### 2.1 Separation of concerns

| Component | Role |
|---|---|
| **Chatwoot** (self-hosted) | Recruiter console — inbox, transcript, agent assignment, labels, notes, status, collaboration |
| **CRM page** (small custom) | VFIC business data — leads, jobs, knowledge |
| **n8n** | Chatbot automation + the Zalo ↔ Chatwoot ↔ Supabase bridge |
| **Supabase / Postgres** | Source of truth for **both** Chatwoot and VFIC data |
| **Zalo OA** | Worker-facing communication channel |

### 2.2 Deployment topology & databases

- **One VPS** hosts: **n8n** (existing), **Chatwoot** (web + Sidekiq worker + **Redis**), and the **small CRM page** (a static build served by nginx, talking to Supabase from the browser).
- **Supabase (cloud)** is a **single Postgres project** holding **two isolated schemas**:
  - `chatwoot` schema — Chatwoot's own tables (contacts, conversations, messages, agents, teams, labels, inboxes), **managed entirely by Chatwoot**. Accessed via a **dedicated Postgres role**.
  - `public` schema — VFIC data (see [§4](#4-data-model)). Accessed by n8n and the CRM page.
- **Redis runs on the VPS** (light); only Chatwoot's Postgres is offloaded to Supabase. Chatwoot connects to Supabase through the **connection pooler (Supavisor)** because Rails/Sidekiq open many connections.

> **Does anything need its own database?** No separate database *server*. There is one Supabase Postgres project; Chatwoot simply manages its own `chatwoot` schema within it, isolated from VFIC's `public` schema. This is **non-standard for Chatwoot** (most self-hosted installs use a dedicated Postgres) — see the risks and escape hatch in [§11.2](#112-chatwoot-on-supabase-risks--mitigations).

### 2.3 Tech stack

- **Chatwoot** (self-hosted, Docker on the VPS) — the inbox/recruiter console, via its **API channel** + webhooks.
- **n8n** (existing) — bot workflow + bridge; uses the existing `zaloBot` node (Zalo) and Postgres node (Supabase `public`).
- **CRM page** — React + TypeScript + Vite + Tabler/Bootstrap (small: leads, jobs, knowledge only); Supabase JS client.
- **Supabase** — Postgres (both schemas), Auth (CRM-page admin login), Storage (KB uploads), optional Realtime.

## 3. Roles & permissions

### 3.1 Roles (two identities, two systems)

- **Recruiters** are **Chatwoot agents** — they authenticate and work inside Chatwoot. No separate login for them.
- **Admin** is a **Chatwoot admin** *and* a **CRM-page admin** (Supabase Auth). The CRM page is **admin-only in the MVP**.

```ts
type UserRole = "admin" | "recruiter";
```

Vietnamese labels: `admin` = **Quản trị viên**, `recruiter` = **Nhân viên tuyển dụng**.

**Simple rule:** admin can access all data; a recruiter can access assigned conversations/leads and can take over unassigned conversations; a recruiter cannot manage system settings, chatbot config, users, or knowledge approval.

### 3.2 Permission matrix (and who enforces it)

| Feature | Admin | Recruiter | Enforced by |
|---|---|---|---|
| Dashboard / inbox | Full | Limited | Chatwoot |
| View all conversations | Yes | No | Chatwoot |
| View assigned / unassigned conversations | Yes | Yes | Chatwoot |
| Take over chat (assign self) | Yes | Yes | Chatwoot → n8n |
| Release chat back to bot | Yes | Yes, only owned | Chatwoot → n8n |
| Send message to worker | Yes | Yes, only owned | Chatwoot → n8n → Zalo |
| Assign / reassign conversation | Yes | No | Chatwoot |
| Close / reopen (resolve) conversation | Yes | Yes, only owned | Chatwoot |
| Labels, internal notes | Yes | Yes | Chatwoot |
| View all leads | Yes | No | CRM page (Supabase RLS) |
| View assigned leads | Yes | Yes | CRM page |
| Edit lead / lead stage | Yes | Yes, only assigned | CRM page |
| Export leads | Yes | No | CRM page |
| Create / update jobs | Yes | No | CRM page |
| View jobs | Yes | Yes | CRM page |
| Upload / approve / archive knowledge docs | Yes | No | CRM page |
| View analytics | Full | Own performance only | CRM page |
| Manage users / chatbot settings / audit log | Yes | No | CRM page |

### 3.3 Navigation

- **Chatwoot sidebar** (recruiters + admin): inbox/conversations, contacts, labels, reports, teams.
- **CRM page sidebar** (admin): Leads / Ứng viên · Việc làm · Kho kiến thức · Báo cáo · Nhật ký hệ thống · Cài đặt chatbot.

## 4. Data model

### 4.1 Ownership split

| Owner | Tables / data |
|---|---|
| **Chatwoot** (`chatwoot` schema, managed by Chatwoot) | contacts, conversations, messages (**the live transcript**), agents, teams, labels, inboxes, conversation status |
| **Supabase `public`** (VFIC) | `conversations` (linkage + `mode`/`status`/`needs_human`/`version`), `leads` (+ `lead_stage`, `intent_score`), `jobs`, `knowledge_documents`, `follow_up_tasks`, `bot_runs` — plus existing `documents`, `memories`, `vfic_chat_histories`, `vfic_message_dedup` |

> **Note:** the earlier design's Supabase `messages` transcript table is **removed** — Chatwoot now owns the transcript. The suppressed-bot-reply concept moves into `bot_runs` (audit). Worker identity is the `leads` row keyed by `zalo_id` (no separate contacts table); it is linked to a Chatwoot contact via `chatwoot_contact_id`.

### 4.2 DDL (Supabase `public` — create as a migration)

```sql
-- enums
CREATE TYPE conversation_mode   AS ENUM ('BOT','HUMAN');
CREATE TYPE conversation_status AS ENUM ('OPEN','CLOSED');
CREATE TYPE bot_run_outcome     AS ENUM ('sent','suppressed','failed');

CREATE TYPE kb_status           AS ENUM ('PENDING','APPROVED','ARCHIVED');
CREATE TYPE follow_up_status    AS ENUM ('PENDING','DONE','SNOOZED','CANCELLED');

-- profiles: CRM-page admin auth (recruiters live in Chatwoot)
CREATE TABLE profiles (
  id        uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,

CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
BEGIN INSERT INTO public.profiles (id) VALUES (NEW.id); RETURN NEW; END; $$;
CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

-- conversations: VFIC linkage to Chatwoot (join key = existing Zalo chat_id)
CREATE TABLE conversations (
  id                          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  zalo_chat_id                text UNIQUE NOT NULL,
  chatwoot_conversation_id    bigint UNIQUE,   -- link to Chatwoot conversation
  chatwoot_contact_id         bigint,          -- link to Chatwoot contact (worker)
  mode                        conversation_mode   NOT NULL DEFAULT 'BOT',
  status                      conversation_status NOT NULL DEFAULT 'OPEN',
  needs_human                 boolean NOT NULL DEFAULT false,  -- "Cần người xử lý"
  version                     int NOT NULL DEFAULT 1,          -- optimistic lock
  assigned_chatwoot_agent_id  bigint,          -- recruiter = Chatwoot agent id
  taken_over_at               timestamptz,
  last_message_at             timestamptz,

  updated_at                  timestamptz NOT NULL DEFAULT now()
);

-- bot_runs: audit of every proposed bot reply (sent or suppressed)
CREATE TABLE bot_runs (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id     uuid NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  proposed_reply      text NOT NULL,
  outcome             bot_run_outcome NOT NULL,
  reason              text,                 -- 'human_took_over' | 'version_mismatch' | 'ok' | …
  mode_at_run_start   conversation_mode NOT NULL,
  version_at_run_start int NOT NULL,
  created_at          timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX bot_runs_conv_idx ON bot_runs (conversation_id, created_at);

-- extend existing leads with CRM stage + Chatwoot linkage
ALTER TABLE leads
  ADD COLUMN lead_stage text NOT NULL DEFAULT 'NEW'
    CHECK (lead_stage IN ('NEW','ENGAGED','QUALIFIED','APPLIED','HIRED','LOST','UNQUALIFIED')),
  ADD COLUMN intent_score numeric,
  ADD COLUMN assigned_chatwoot_agent_id bigint,
  ADD COLUMN chatwoot_contact_id bigint,
  ADD COLUMN chatwoot_conversation_id bigint;
-- (legacy leads.status text column is superseded by lead_stage; migrate/align during impl.)

-- jobs
CREATE TABLE jobs (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  title        text NOT NULL,
  description  text,
  location     text,
  requirements text,
  salary_range text,
  status       job_status NOT NULL DEFAULT 'ACTIVE',
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);

-- knowledge_documents: approval lifecycle (embeddings stay in the `documents` vector table)
CREATE TABLE knowledge_documents (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  title         text NOT NULL,
  source        text,                 -- 'google_drive' | 'manual' | …
  drive_file_id text,                 -- links to documents.drive_file_id
  status        kb_status NOT NULL DEFAULT 'PENDING',
  approved_by   uuid REFERENCES profiles(id),
  approved_at   timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

-- follow_up_tasks
CREATE TABLE follow_up_tasks (
  id                          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  lead_id                     bigint NOT NULL REFERENCES leads(id) ON DELETE CASCADE,
  assigned_chatwoot_agent_id  bigint,
  due_at                      timestamptz,
  note                        text,
  status                      follow_up_status NOT NULL DEFAULT 'PENDING',
  created_at                  timestamptz NOT NULL DEFAULT now(),
  updated_at                  timestamptz NOT NULL DEFAULT now()
);

-- updated_at helper
CREATE OR REPLACE FUNCTION public.touch_updated_at() RETURNS trigger
  LANGUAGE plpgsql AS $$ BEGIN NEW.updated_at=now(); RETURN NEW; END; $$;
CREATE TRIGGER conversations_touch BEFORE UPDATE ON conversations
  FOR EACH ROW EXECUTE FUNCTION public.touch_updated_at();
```

### 4.3 Field decisions

- `mode` {BOT, HUMAN} — **who is handling** the chat.
- `status` {OPEN, CLOSED} — **lifecycle** (mirrors Chatwoot open/resolved).
- `needs_human` (boolean) — the **"Cần người xử lý"** escalation flag (chosen over a third `PENDING_HUMAN` mode value).
- `version` — optimistic lock; bumped on every ownership transition.
- `chatwoot_conversation_id` / `chatwoot_contact_id` / `assigned_chatwoot_agent_id` — link VFIC rows to Chatwoot entities (Chatwoot uses integer ids).
- Recruiter identity is the **Chatwoot agent id** (no Supabase FK to a recruiter table).
- `bot_runs` stores the bot's **proposed reply** even when suppressed, so it's auditable.

## 5. Human takeover (core feature)

### 5.1 Requirement & the "cancel" problem

When a recruiter takes over, the chatbot must stop immediately and any in-flight bot reply must not reach the worker.

n8n executions **cannot be cancelled externally**, so "cancel the pending bot reply" describes the *outcome*, not the mechanism. The model is **check-before-send**: the bot checks whether it still owns the conversation and, if not, silently drops the reply. The takeover itself is now triggered from **Chatwoot** (agent assignment) via webhook — not a custom button.

### 5.2 Mechanism — two guard points (unchanged)

1. **Run-start guard** — when a new inbound arrives, if `mode = HUMAN` the bot logs the worker's line (and mirrors it into the Chatwoot transcript) and **stops**: no typing, no AI.
2. **Pre-send guard** — immediately before the Zalo send, re-check `mode = 'BOT' AND version = version_at_start`. If it fails, write a `bot_runs` row with `outcome = 'suppressed'` (storing the proposed reply) and **stop**.

`take_over_conversation()` is an **atomic** flip (`mode → HUMAN`, `version++`) that the bot's guard then observes. Checking both `mode` and `version` also kills **stale** runs (e.g. take over → release during one run). The only unavoidable residual window is the sub-second gap between the pre-send check and the Zalo HTTP call.

### 5.3 Takeover / release RPCs (invoked by n8n on Chatwoot webhooks)

```sql
CREATE OR REPLACE FUNCTION public.take_over_conversation(p_zalo_chat_id text, p_chatwoot_agent_id bigint)
RETURNS uuid LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
DECLARE v_conv uuid; v_owner bigint;
BEGIN
  SELECT assigned_chatwoot_agent_id INTO v_owner FROM conversations WHERE zalo_chat_id=p_zalo_chat_id;
  IF v_owner IS NOT NULL AND v_owner <> p_chatwoot_agent_id THEN
    RAISE EXCEPTION 'conversation already owned by another recruiter';
  END IF;
  INSERT INTO conversations (zalo_chat_id, mode, assigned_chatwoot_agent_id, taken_over_at, version)
  VALUES (p_zalo_chat_id,'HUMAN',p_chatwoot_agent_id,now(),2)
  ON CONFLICT (zalo_chat_id) DO UPDATE
    SET mode='HUMAN', assigned_chatwoot_agent_id=p_chatwoot_agent_id, taken_over_at=now(),
        needs_human=false, version=conversations.version+1
  RETURNING id INTO v_conv;
  RETURN v_conv;   -- n8n may post a Chatwoot activity/label; no Supabase messages table
END; $$;

CREATE OR REPLACE FUNCTION public.release_to_bot(p_zalo_chat_id text, p_chatwoot_agent_id bigint)
RETURNS uuid LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
DECLARE v_conv uuid;
BEGIN
  UPDATE conversations SET mode='BOT', version=version+1
  WHERE zalo_chat_id=p_zalo_chat_id AND assigned_chatwoot_agent_id=p_chatwoot_agent_id
  RETURNING id INTO v_conv;
  IF v_conv IS NULL THEN RAISE EXCEPTION 'not owner or not found'; END IF;
  RETURN v_conv;
END; $$;
```

### 5.4 The Chatwoot ↔ n8n bridge

- **Inbound (worker → bot):** Zalo webhook → n8n → (a) Chatwoot API: ensure contact (keyed by `zalo_id`) + create incoming message; (b) Supabase: ensure `conversations` row; (c) run the bot.
- **Bot reply:** n8n generates the reply → pre-send guard (Supabase) → if ok, send to Zalo **and** mirror the reply into the Chatwoot transcript via API.
- **Takeover:** recruiter is **assigned** in Chatwoot → `conversation_updated` webhook → n8n → `take_over_conversation()` → `mode=HUMAN`. Subsequent bot runs are suppressed.
- **Recruiter reply:** agent sends a message in Chatwoot → `message_created` (outgoing) webhook → n8n → send to Zalo (Zalo OA token stays in n8n).
- **Release to bot:** resolve the Chatwoot conversation (or apply a "hand-to-bot" label) → webhook → n8n → `release_to_bot()` → `mode=BOT`; append the human turns into `vfic_chat_histories` so the bot's memory is continuous.

### 5.5 n8n bot modifications

Edit **`VFIC-Chatbot.json`** (id `iodmXzjRe03KqPdB`) **in place**; keep `active:false` until tests pass. Add: Ensure Conversation (capture `version_at_start`), Insert Inbound to Chatwoot (API), Run-Start Guard, Recheck Ownership + Pre-Send Guard before the existing `zaloBot` send, and write a `bot_runs` row (sent or suppressed). Reuse the existing Postgres account credential and `zaloBot` node. (For free-text inserts prefer the Postgres `insert` op over `executeQuery`'s comma-separated `queryReplacement`.)

A **second n8n workflow** handles Chatwoot webhooks (`conversation_updated`, `message_created`) → calls the RPCs / sends to Zalo.

## 6. Security & realtime

### 6.1 Two auth surfaces

- **Chatwoot** manages agent/admin accounts, roles, and access to the inbox (its own auth; data in the `chatwoot` schema).
- **CRM page** uses **Supabase Auth** + a `profiles.role` check; **RLS** protects VFIC tables. Enabling RLS alone is insufficient — `GRANT` privileges to `authenticated` (anon gets nothing).

```sql
ALTER TABLE conversations, leads, jobs, knowledge_documents, follow_up_tasks, bot_runs, profiles
  ENABLE ROW LEVEL SECURITY;
GRANT SELECT, INSERT, UPDATE, DELETE ON
  conversations, leads, jobs, knowledge_documents, follow_up_tasks, bot_runs, profiles TO authenticated;

-- MVP: CRM page is admin-only. (Recruiter-scoped policies added when recruiters get CRM access.)
CREATE POLICY vfic_admin_all ON profiles FOR SELECT TO authenticated
  USING (EXISTS (SELECT 1 FROM profiles p WHERE p.id=auth.uid() AND p.role='admin'));
-- ... FOR ALL admin policies on each VFIC table (USING/WITH CHECK role='admin') ...
```

> n8n's direct Postgres connection bypasses RLS (trusted infra), so bot writes are unaffected.

### 6.2 Realtime

- **Chatwoot** has its own realtime inbox (no extra work).
- **Supabase Realtime** is **optional** — only if the CRM page wants live lead/follow-up updates. If used, enroll the tables and set `REPLICA IDENTITY FULL`; Realtime respects RLS, so per-user scoping is automatic.

## 7. Feature & page specs

### 7.1 Conversation inbox & detail → **Chatwoot**

Provided by Chatwoot (no custom build): inbox list, live transcript, filters, agent assignment, labels, internal notes, conversation status (open/pending/resolved), teams, basic reports. **Conversation filters** map to Chatwoot views/labels: Tất cả · Của tôi · Chưa phân công · Cần người xử lý · Bot đang xử lý · Tôi đang xử lý · Đã đóng.

**Takeover** = assigning the conversation (self or auto-assign). **Release to bot** = resolving or a "hand-to-bot" label. **Recruiter send** = typing in Chatwoot.

### 7.2 Leads → CRM page

Routes `/leads` (admin: all) and `/my-leads` (recruiter: assigned). **Lead stages:** `NEW · ENGAGED · QUALIFIED · APPLIED · HIRED · LOST · UNQUALIFIED` (implemented as `leads.lead_stage`; `HANDED_OFF` removed — handoff = `assigned_chatwoot_agent_id IS NOT NULL`). `intent_score` captures qualification strength.

### 7.3 Jobs → CRM page

Admin: create / edit / activate / pause / mark full / archive. Recruiter: view active jobs, search, copy, recommend to a worker.

### 7.4 Knowledge base → CRM page

Admin-only (MVP): upload document, preview extracted text, approve, archive, re-run embedding, test retrieval. (Embeddings live in the `documents` vector table; `knowledge_documents` holds the approval lifecycle.)

### 7.5 Follow-up → CRM page

Admin sees all; recruiter sees their own pending/overdue/completed. Create for an own lead, mark done, snooze, cancel.

## 8. Acceptance tests

1. **Bot chat mirrors to Chatwoot** — worker sends a Zalo message → a Chatwoot contact + conversation exist, the inbound message and the bot reply both appear in the transcript.
2. **Takeover via Chatwoot assignment** — assign the conversation in Chatwoot → `conversation_updated` webhook → `mode=HUMAN`, `version++`; the bot's in-flight reply is **suppressed** (a `bot_runs` row with `outcome='suppressed'`) and **no** bot message is sent to Zalo.
3. **Run-start guard** — with `mode=HUMAN`, an inbound is mirrored to Chatwoot but produces no AI run and no Zalo send.
4. **Recruiter reply** — agent replies in Chatwoot → `message_created` webhook → the message is delivered to the worker via Zalo.
5. **Stale-run** — take over then release within one run → original reply suppressed (version mismatch); a new inbound after release → fresh `sent` bot reply.
6. **Idempotency** — replay the same Zalo inbound → single Chatwoot message / single `conversations` row.
7. **Double-takeover** — two recruiters assigned concurrently → exactly one wins (the other raises).
8. **Release to bot** — resolve/label → `mode=BOT`, `version++`; human turns appended to `vfic_chat_histories`; the bot resumes with context.
9. **Bot guardrail** — off-topic input → short redirect, no invented answer.
10. **Lead qualification** — worker states preference/location/availability → `lead_stage=QUALIFIED`, reasons saved, follow-up task created.

Flip `VFIC-Chatbot` to `active:true` only after tests 1–5 pass.

## 11. Notes & references

### 11.1 Takeover feature status against the current system

Most of the data layer is **greenfield** (no `conversations`/`bot_runs`/`jobs`/`knowledge_documents`/`follow_up_tasks`; no `mode`/`version`; no Chatwoot). The bot workflow needs the guard nodes and a new Chatwoot-webhook workflow. The CRM page is new. The live transcript is delegated to Chatwoot.

### 11.2 Chatwoot-on-Supabase risks & mitigations

This design points Chatwoot at the **shared Supabase project** (non-standard). Risks and mitigations:

- **Schema/migration ownership:** Chatwoot must own its tables. → Run Chatwoot in a **dedicated `chatwoot` schema** with a **dedicated role**; never let VFIC migrations touch it.
- **Connection limits:** Rails + Sidekiq open many connections. → Connect via Supabase's **pooler (Supavisor)**; size the plan's connection limit accordingly.
- **Postgres version:** Chatwoot requires a recent Postgres (13+). → Confirm the Supabase project version meets it.
- **Coupling:** a Chatwoot migration or Supabase incident affects both. → **Escape hatch:** split Chatwoot to a **second Supabase project** or its **own Postgres** (on-VPS or managed) if problems arise. The VFIC `public` schema is unaffected either way.

### 11.3 Chatwoot integration references

- API channel inbox (Settings → Inboxes → API, with callback/webhook URL).
- REST: create contact / conversation / message; contacts can auto-create.

### 11.5 Known exposure to close (existing tables)

Two existing tables have permissive read policies that expose data to anyone
holding the project's `anon` key. The `anon` key is **public by design** (it
ships in any frontend bundle and is visible in the dashboard/repo), so the
exposure is effectively **live**, not latent:

- **`leads`** — policy "Allow read on leads" grants `SELECT` with `USING=true` to
  the `public` (everyone) role. Exposes PII (name, phone, address, …).
- **`vfic_chat_histories`** — policy "Allow anon read on vfic_chat_histories"
  grants `SELECT` with `USING=true` to `anon`. Exposes full chat history.

RLS is enabled on both, but `USING=true` defeats it for reads. Close by replacing
these with admin-only policies and revoking `anon` (after the `profiles` table in
[§4.2](#42-ddl-supabase-public--create-as-a-migration) exists). n8n is unaffected
because it connects with the `service_role` key, which bypasses RLS.

```sql
-- leads: authenticated admins only
DROP POLICY IF EXISTS "Allow read on leads" ON leads;
CREATE POLICY leads_admin_all ON leads FOR ALL TO authenticated
  USING (EXISTS (SELECT 1 FROM profiles p WHERE p.id = auth.uid() AND p.role='admin'))
  WITH CHECK (EXISTS (SELECT 1 FROM profiles p WHERE p.id = auth.uid() AND p.role='admin'));
REVOKE ALL ON leads FROM anon;

-- vfic_chat_histories: bot uses service_role; no anon/authenticated read needed
DROP POLICY IF EXISTS "Allow anon read on vfic_chat_histories" ON vfic_chat_histories;
REVOKE SELECT ON vfic_chat_histories FROM anon, authenticated;
```

This is an **RLS fix, not a key rotation** — the `anon` key is meant to be public;
the lock is the policy.
